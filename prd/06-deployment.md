# 06. 本番配置とビルド

> **本章はすべて実施済み。** [§3](#3-本番イメージ)の本番イメージ（esbuild + distroless）と
> [§4](#4-スキーマの反映)のマイグレーション（Phase 3-1）に加え、
> [§2](#2-配信の形)・[§5](#5-前段プロキシが満たすべき条件)の**前段への配置**も済み、
> [§6](#6-検証)の疎通確認を**否定側も含めて通っている**（[05](./05-roadmap.md) Phase 3-2）。
> 配置の具体はリポジトリ外にある（[§7](#7-秘匿方針)）。
> **レート制限と前段の認証は [04](./04-auth-and-privacy.md) が正典**、本章はビルドと配置を扱う。

Phase 1・2 は開発環境（`pnpm dev` / 前段プロキシ越しの remote dev）で完結していた。
本章は、そこから**本番として常設する**ために足りないものを定める。

## 1. 何が足りないか

開発環境は**Vite の dev サーバーが唯一の外向きの口**で、`/api` と `/s` だけをアプリへ転送している
（[01](./01-architecture.md) §3）。本番にはこの転送が無い。加えて:

- `packages/server` の `build` は `tsc --noEmit` = **型検査であって出力ではない**
- 本番用のイメージが無い（`Dockerfile.dev` のみ）
- スキーマの反映が `db:push`（**使い捨て DB 向け**）しか無い

## 2. 配信の形

**前段プロキシが静的資産を直接配り、`/api` と `/s` だけをアプリへ転送する。**
アプリは API と共有パスだけを持ち、静的ファイルを配らない。

**理由は、既にある本番環境と形を揃えることである。** 別の配置先では前段プロキシが同じ役割を
担っており、そちらへ移すときに**構成ごと持っていける**。アプリ側で静的配信まで抱えると、
移設先の前段と役割が二重になる。

⚠ **帰結として、`/api`・`/s`・静的の振り分けが前段の設定に載る。**
これは**リポジトリの外**であり、型検査もレビューも PRD も届かない。開発環境で
「`/s` を転送設定に足すまで、実装済みの経路が静かに `index.html` を返す」罠を実際に踏んでいる
（[01](./01-architecture.md) §3）。**同じ失敗が本番でも起こりうる**ため、[§6](#6-検証) の
疎通確認でのみ担保する。

## 3. 本番イメージ

**esbuild で単一 ESM にバンドルし、Node だけを含む最小イメージ（distroless）で実行する。**
既存リポジトリと同じ形である（[01](./01-architecture.md) §1 の「揃える」判断）。

| 段 | 内容 |
|---|---|
| build | `node:22-slim` + pnpm。`--frozen-lockfile` で依存を解決し、esbuild でバンドル |
| runtime | distroless（Node のみ）。**バンドル済みの JS だけを置き、`node_modules` を持たない** |

- **エントリは 2 つ**: サーバー本体と、マイグレーション（[§4](#4-スキーマの反映)）。
  同じイメージに同梱する。
- ⚠ **`packages/server` の `build` の意味が変わる**（型検査 → バンドル出力）。
  型検査は `pnpm typecheck` が担い、検証チェーン（`typecheck && test && check && build`）は
  そのまま通る。
- **出力の拡張子は `.mjs`。** 実行環境に `package.json` を置かないため、`.js` のままだと
  ESM か CJS かの判定を Node の推測に委ねることになる。**`.mjs` は常に ESM** なので、
  判定の余地そのものが無くなる（shell が無く、最終段で `package.json` を生成できないことへの
  対処でもある）。
- ⚠ **distroless には shell が無い。** `docker compose exec <service> sh` は使えない。
  ただし ENTRYPOINT が Node なので、**JS のパスを渡す形での実行は可能**である
  （[§4](#4-スキーマの反映) がこれを使う）。

### 静的資産

**ホストでビルドし、前段が配る場所へ置く。**

- `import.meta.env` も `VITE_*` も使っていないため、**`dist` は環境非依存**である。
  ビルドに env を渡す必要がない。
- ⚠ **検証とビルドと配置を 1 本に連結する**（`typecheck && test && check && build && 配置`）。
  途中で落ちたら配置しない。**「ビルドを忘れたまま更新して、古い画面が新しい API を叩く」**が
  この方式の唯一かつ最大の失敗形である。
- ⚠ **古い資産を消してから置くため、その間だけ 404 になる窓がある。** 個人用ツールとして
  許容するが、**更新中に画面が壊れる瞬間がある**ことは認識しておく。

## 4. スキーマの反映

**dev は `db:push`（強制同期）、本番は `db:generate` → `db:migrate`（バージョン管理）。**

`push` は差分を推測して DDL を出すため、**列のリネームを削除 + 追加と解釈しうる**。
dev では「使い捨て」と割り切って正しい判断だが、本番では**黙ってデータを消す経路**になる。
このアプリの価値は溜めたものそのものなので、バックアップより先に**壊さない仕組み**を置く。

### マイグレーションはイメージに同梱する

**生成した SQL と適用用のエントリを本番イメージに入れ、使い捨てコンテナとして実行する。**

- **`drizzle-kit` は入らない。** SQL を*生成*するのが `drizzle-kit`（dev 専用）で、
  *適用*するのは `drizzle-orm` の migrator——**こちらは元から本番の実行時依存**である。
- **資格情報も入らない。** 接続先は実行時に環境変数から渡る。
- **ホストへ DB ポートを公開しない。** 到達は compose 網の中で完結する
  （[01](./01-architecture.md) §3 の「db をホストに公開しない」を本番でも崩さない）。

**同梱する理由は、ポートを開けずに済むことではない。**

> **マイグレーションとコードのバージョンが、構造的に一致する。**

外部から適用する方式は「**手元にある SQL** を、**本番で動いているイメージ**へ流す」ことになり、
両者がずれても何も警告されない。同じイメージの中身なら、ずれが原理的に起きない。

### ⚠ ロールバックは存在しない

**drizzle に down migration は無い**（コマンドは `generate` / `migrate` / `pull` / `push` /
`studio` / `up` / `check` / `export` のみ。`up` は古い形式のファイルを新形式へ変換するもので、
`migrate` の逆ではない）。**これは適用方式の選択と無関係である。**

戻すときは**逆 SQL を手で流し、記録テーブルの行を消す**。その経路は既にある——
**DB のコンテナには shell と `mysql` クライアントが入っている**ので、`docker compose exec` で届く。
distroless なのはアプリだけである。

### ⚠ 起動時の自動マイグレーションにはしない

失敗したときの挙動と、将来インスタンスを増やしたときの競合が読めなくなる。
**明示的な一手として残す。**

## 5. 前段プロキシが満たすべき条件

**前段の具体（製品名・ドメイン・設定構文・ポリシー）は公開文書に書かない**
（[README](./README.md) §秘匿方針）。ここに書くのは**アプリが成立するための要件**だけである。

| # | 要件 | 満たさないと |
|---|---|---|
| 1 | `/api` と **`/s/` 配下**をアプリへ転送し、**それ以外は静的配信 + SPA フォールバック** | 実装済みの経路が静かに `index.html` を返す |
| 2 | **`/s/` 配下だけが無認証で到達でき、それ以外は前段の認証を通る** | 共有が成立しない（広げるとアプリ全体が無認証公開になる。[04](./04-auth-and-privacy.md) §4） |
| 3 | **アプリへの到達経路が前段だけであること** | 前段の認証もレート制限も迂回できる |
| 4 | **レート制限を持つ**（`/s` と認証の口） | [04](./04-auth-and-privacy.md) §2 の前提が崩れる |
| 5 | **クライアント IP を復元してからレート制限をかける** | 全リクエストが同一 IP に潰れ、**制限が自分を締め出す装置になる** |
| 6 | **アプリが停止していても前段が起動できること** | 1 つ落ちただけで前段全体が上がらなくなる |

### ⚠ 要件 2 の境界は「`/s/` プレフィックスちょうど」である

**素通しにする範囲は `/s` で始まる文字列ではなく、`/s/` 配下に限る**
（[04](./04-auth-and-privacy.md) §4）。前置一致で `/s` を指定すると、**`/src` のように
`/s` で始まるだけの別のパスまで認証を迂回する**。将来 `/settings` のような経路を足せば、
それも黙って巻き込まれる。

**これは推測ではなく、開発環境で実際に踏んだ事故である。** `vite.config.ts` の転送設定が
`'/s'` ではなく `'^/s/'`（区切りまで含む形）を使っているのは、前置一致で `/src/*` まで
転送されて画面が真っ白になったためである（[01](./01-architecture.md) §3）。
**前段でも同じ間違いが成立し、そちらの帰結は「画面が壊れる」ではなく「認証が外れる」になる。**

⚠ **境界の過不足は、肯定側の確認では絶対に見つからない。** `/s/<token>` が通ることは
広すぎる設定でも成り立つ。**[§6](#6-検証) の否定側（`/s` で始まる非共有パスが認証を要求すること）が
唯一の検出手段である。**

⚠ **3 と 5 は 2 つで 1 組である。** クライアント IP を前段のヘッダから復元する設定を入れた
プロキシに**前段を通さず直接届く経路があると、ヘッダを詐称してレート制限を無限にすり抜けられる**。
「復元する」と「前段以外から届かない」は、**どちらか片方では意味を持たない**。

## 6. 検証

**設定を触ったら必ず流す。否定側の確認が本体である**（[04](./04-auth-and-privacy.md) §4 と同じ姿勢）。

| 対象 | 期待 | 外れたときの意味 |
|---|---|---|
| `/` | 200 + `text/html` | 静的配信が死んでいる |
| ハッシュ付き資産 | 200 | 配置が失敗している（[§3](#静的資産)） |
| `/api/auth/me` | **401** | 404 なら `/api` が転送されていない。200 なら認証が壊れている |
| **`/s/<存在しないトークン>`** | **404** | ⚠ **最重要。** 200 + `text/html` なら**転送されず SPA フォールバックに落ちている** |
| 存在しないパス | 200 + `index.html` | SPA フォールバックが効いていない |
| `/s/<トークン>` への連打 | 制限が発動する | レート制限が効いていない（**無認証で開いている唯一の経路**） |
| 認証が要る経路（`/`・`/api/*`） | 前段の認証へ送られる | **本体が無認証で公開されている** |
| `/s/<トークン>` | 前段の認証へ送られ**ない** | 共有が成立しない |
| **`/s` で始まる非共有パス**（`/src/...` 等） | **前段の認証へ送られる** | ⚠ **素通しの範囲が広すぎる**（§5 の要件 2）。前置一致で `/s` を例外にしている |

⚠ **ステータスコードだけでは足りない。`Content-Type` まで見る。**
`/s` の失敗形は「200 + HTML」であり、404 だけを見ていると**転送忘れを見逃す**。

⚠ **レート制限の確認は、逐次に叩いても成立しない。** 公開経路では 1 往復に前段のぶんの
遅延が乗るため、**順番に投げるだけでは実効レートが制限の閾値に届かない**。制限が正しく
効いていても「発動しなかった」と出る。**並列で投げること。**

⚠ **クライアント IP の復元（[§5](#5-前段プロキシが満たすべき条件) 要件 5）は、この表からは
確かめられない。** 制限が発動したことは、復元された IP でも前段の IP でも等しく起こりうる。
**前段のアクセスログに出る接続元が、前段自身の IP ではなく実際のクライアントの IP に
なっていることを見る**——これが唯一の確認手段である。
