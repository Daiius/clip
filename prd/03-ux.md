# 03. 投入と閲覧

> **実装済み**: 投入口（ページへのペースト / 貼り付けボタン / D&D /
> ファイル選択）と判別・即保存（§1）/ 新しい順の一覧とプレビュー・折りたたみ（§2）/
> **規模の表示と切り替え**（§2.1）/ クリックでコピー・ダウンロード（§3）/ 確認付きの削除（§4）/
> **狭い幅でのアイコン化**を含むレスポンシブ（§5）。
> **§6（共有）と §2 の選択チェックボックス**（Phase 2）。**本章は全て実装済み。**

## 1. 投入

**テキストの入力欄を作らない。** 文字を打ち込む場所は用意せず、**貼られたものが増えていくだけ**にする。
「何かを書く道具」ではなく「受け渡しの中継点」であることを、UI の形で表す。

| 経路 | 操作 | 端末 |
|---|---|---|
| **ページへのペースト** | 画面上で `⌘`/`Ctrl` + `V`（どこにもフォーカスせずに） | Windows / MacBook |
| **貼り付けボタン** | 1タップ → OS の許可 → クリップボードを読む | **iPhone**（§1.3） |
| ドラッグ&ドロップ | 画像ファイルを画面に落とす | Windows / MacBook |
| ファイル選択 | 写真アプリ / ファイルから選ぶ | 全端末 |

### 1.1 判別と保存

貼られた中身を見て `kind` を決める。**人間に選ばせない。**

- ペーストは `ClipboardEvent.clipboardData`、D&D は `DataTransfer` を見て、
  **ファイルが含まれていれば `image`、なければ `text`** として扱う。
- **クライアント側で申告 MIME を見て allowlist 外と判断し、送る前に弾かない**（**すべての経路**。
  貼り付けボタン（§1.3）も、ファイル選択の `accept` 属性も例外ではない）。
  `File.type` は申告値にすぎず、**正しい PNG や JPEG でも空文字や `application/octet-stream`
  になることがある**。ここで弾くと、正しい画像が §1.2 のシグネチャ検証に到達しないまま
  拒否されてしまう。形式の判定は**サーバー1箇所に集約する**。
- **すべて即保存する。** 確認ダイアログも保存ボタンも確定操作も挟まない。
  テキストも画像も、**貼られた瞬間に1エントリとして一覧の先頭に増える**。
- 入力欄が無いため「入力途中の状態」が存在せず、保存タイミングの判断が要らない。

### 1.2 受け付ける形式

**画像は PNG / JPEG / GIF / WebP のみ受け付ける。**

- **SVG は受け付けない。** SVG は能動コンテンツ（スクリプトを含みうる）であり、
  private データと同一オリジンから inline 配信すると、開いた瞬間にアプリのオリジンで実行され、
  認証済み API を操作されうる（stored XSS）。**自分で貼ったものだけとは限らない**
  （他人からもらった画像を中継する用途がある）ため、形式で弾く。
- **クライアントが申告した MIME を信用しない。** サーバーが実体の先頭バイト（ファイルシグネチャ）から
  形式を判定し、allowlist 外なら保存しない（[02](./02-data-model.md) §4）。
- テキストは形式を問わない（プレーン文字列として保存する）。

### 1.3 iPhone での経路

**iOS Safari はページに `paste` イベントを配らない。** `input` / `contenteditable` にフォーカスが
ある時しか発火せず、「ページに向かって貼り付ける」操作自体が OS に存在しない。
**ペースト一本では iPhone から投入できない。**

そこで **「貼り付け」ボタン**を置き、押されたら `navigator.clipboard.read()` でクリップボードを読む。

- `clipboard.read()` は**ユーザー操作の中でのみ**許可され、OS の貼り付け許可 UI が出る（iOS 13.4+）。
- **これは入力欄ではない**ので、「打ち込む場所を作らない」という方針と矛盾しない。
- 読み取りが拒否・失敗した場合は、**その旨を表示して「画像を選ぶ」に誘導する**。
  ⚠ **ファイル選択に `accept` を付けない**（§1.2）。デスクトップの `accept` は候補を絞るだけの
  誘導だが、**iOS のピッカーは条件に合わないものをグレーアウトし、「すべてのファイル」へ
  切り替える逃げ道が無い**。OS が正しい画像を空文字や `application/octet-stream` と申告すると、
  **この案内先で選ぶことすらできなくなる**。
  ⚠ **自動でファイル選択を開くことはできない。** 権限 UI を経た後の時点では、クリック由来の
  transient user activation が切れており、iOS Safari はファイル選択を無視する。
  自動で開こうとすると「押しても何も起きない」状態になるので、**利用者の次のタップに委ねる**。
- ボタンはデスクトップでも常に見える位置に置く（iPhone だけの特別扱いをしない）。デスクトップでは
  `⌘`/`Ctrl` + `V` の方が速いが、経路を分岐させない。

### 1.4 エラー

いずれも**保存せず**、理由を表示する。

- 画像が 20MB 超過（[02](./02-data-model.md) §5）→ 「画像が大きすぎます（20MB まで）」
- テキストが上限超過（[02](./02-data-model.md) §5）→ 「テキストが大きすぎます」
- allowlist 外の形式（SVG・PDF・zip 等）→ 「PNG / JPEG / GIF / WebP のみ扱えます」
- 保存失敗 → 投入した内容を**画面から消さない**。貼り直しを強いない。

**画像の大きさだけは、送る前にクライアント側でも弾く。** 20MB 超をアップロードしきってから
413 で捨てるのは、モバイル回線では待ち時間も通信量も無駄になる。上限値は server の定数を
**web から直接参照する**（書き写すと、上限を上げたときにクライアントだけが古い値のまま厳しくなり、
正しい画像が投入できなくなる）。**同じ事情には同じ文言を出す**ため、事前検査とサーバーの 413 は
同一のメッセージを使う。

⚠ **事前に弾いてよいのは `File.size`（実測値）だけ。** 形式の判定は §1.2 のとおり
サーバーのシグネチャ検証に集約したままにする。申告 MIME による事前の遮断は、
**利用者が回避できない誤判定**を生むので行わない。

**投入は同時に走りうる**（ページへのペーストと D&D は、保存中でも新しい投入を始められる）。
そのため失敗は**投入1件ごとに保持し、それぞれを個別に再試行できる**ようにする。
まとめて1つの状態にすると、**同時に走った別の投入の成功が、失敗した内容と再試行導線を消す**。

## 2. 一覧

**新しい順の時系列のみ。** 検索・タグ・絞り込みは持たない（[05](./05-roadmap.md) §未実装）。

- **50件ずつ**読み込む。並び順は `id`（ULID）の降順単独で、ページングのカーソルも `id`
  （[02](./02-data-model.md) §2）。
- 受け渡し用途では目的のものは大抵一番上にあるため、**最上部が最新**であることを最優先にする。
- 各エントリに表示するもの: **選択のチェックボックス**（§6）、中身のプレビュー、作成時刻、
  **規模**（§2.1）、操作。

### 2.1 規模の表示

**どれくらいのものを受け渡そうとしているのかを分かるようにする。** 目的はデータ通信量の把握で、
回線の細い端末から開くこともあるため、開く前に見当が付く必要がある。

作成時刻と操作の間に置き、**タップするとデータ量（KB / MB）に切り替わる**。

| 種別 | 既定の表示 | タップ後 |
|---|---|---|
| テキスト | `x 文字` | UTF-8 のバイト数 |
| 画像 | `w × h` | バイト数 |
| 壊れているもの | **出さない** | — |

- **文字数はコードポイントで数える。** UTF-16 のコード単位で数えると絵文字が 2 になり、
  見た目の数から離れる（`fileName` を 255 コードポイントで丸めるのと同じ基準。[02](./02-data-model.md) §5）。
- **テキストの文字数とバイト数は、走査1回・追加確保なしで数える。** テキストの上限は
  16,777,215 バイトで（[02](./02-data-model.md) §5）、一覧は 50 件を一度に描画する（§2）。
  本文全体分の配列や UTF-8 バッファを描画のたびに作ると、**正規の保存データだけでタブが停止しうる。**
  バイト数の数え方はサーバーの上限判定（`Buffer.byteLength(text, 'utf8')`）と揃える。
  揃えないと、**投入できる大きさと画面の表示が食い違う**（対を成さないサロゲートも同じく
  U+FFFD の 3 バイトとして数える）。
- **単位は 1024 刻み。** 上限が `20 * 1024 * 1024` で定義されている（[02](./02-data-model.md) §5）ため、
  1000 で割ると上限ちょうどの画像が「21.0 MB」と出て**上限表示と食い違う**。
- **画像の原寸は DB に持たず、読み込んだ `img` から取る。** 「サムネイルを作らず**原寸を CSS で
  縮小**する」（[05](./05-roadmap.md) §確定事項）ので、表示に使う画像は常に原寸そのものである。
  **すでに手元にある寸法を、サーバーで解析し直して列に持つ理由がない**（JPEG の SOF 走査や
  WebP の3系統の書き分けを、得るもの無しに抱えることになる）。
  → 将来サムネイルを入れて原寸を読まなくなったら、そのとき初めて列に持つことを検討する。
- 読み込みが終わるまでは原寸が分からないので、**その間はデータ量だけを出し、ボタンにしない**
  （押しても何も起きない当たりを作らない）。
- 壊れた行に規模を出さない。**中身が取れないものの大きさを語ると、取り出せるように読める。**

### プレビュー

| 種別 | 表示 |
|---|---|
| テキスト | **プレーン表示**（等幅）。Markdown としてレンダリングはしない。長いものは折りたたみ、展開できる |
| 画像 | **原寸を CSS で縮小**して表示 |
| 壊れているもの | **「壊れています。削除してください」と明示する**（下記） |

**壊れた項目を黙って隠さない。** 削除の途中失敗で実体を失った行は、一覧に残して
「実体が見つかりません」と表示する（[02](./02-data-model.md) §3.2）。コピーとダウンロードの
導線も出さない（押しても失敗するため）。**壊れた画像アイコンだけを出して放置しない。**

**Markdown をレンダリングしない理由**: 貼るのは受け渡し対象の文字列そのものであり、
整形されると「元の文字列が何だったか」が分からなくなる。**貼ったものがそのまま見えることを優先する**。

**サムネイルを生成しない理由**: 実装と失敗時のフォールバックを MVP に持ち込まないため
（[05](./05-roadmap.md) §未実装）。回線で重いと感じたら後から足す。

## 3. 取り出し

別端末で受け取るための操作。**カード本体をクリック（タップ）したらクリップボードにコピーされる。**
コピーボタンを探させない。

| 種別 | クリック時の挙動 |
|---|---|
| テキスト | `navigator.clipboard.writeText()` で文字列をコピー |
| 画像 | `navigator.clipboard.write()` で画像をコピー。**未対応・失敗時はダウンロードにフォールバック** |

- コピーできたことが分かるフィードバックを必ず出す（何も起きないと成否が分からないため）。
- ⚠ **クリップボード経由の往復は、バイト列を保存しない。** iPhone で画像をコピーして貼り直すと、
  **OS が再エンコードするので元と異なる大きさになる**（実測: 38,907 → 58,128 バイト）。
  この道具は**見て確かめられるものを受け渡す**ためのものであり、**バイト列を保つ転送路ではない**。
  原本が要るときは**ダウンロード**を使う（そちらは実体をそのまま返す。[02](./02-data-model.md) §4.2）。
- **ダウンロードボタンは別に置く**（`Content-Disposition: attachment`）。iPhone では
  クリップボードより写真アプリへ保存したい場面があるため、コピーだけに寄せない。
- 画像の拡大表示もカード本体クリックとは別の操作にする（クリック＝コピーと衝突させない）。

**タップの意味を、場所で1つに保つ。** 「カード本体＝コピー」以外のタップ（**選択**（§6）、
規模の表示の切り替え（§2.1）、ダウンロード、削除）は、**すべてプレビュー本体の外**（ヘッダ行）に置く。
プレビューの中に別の意味のタップを入れない。**押した場所で何が起きるかが決まる**状態を保てなくなり、
「コピーしたつもりが別のことが起きる」が生じる。

**この原則は「場所」についてのものであり、「モード」を許すものではない。** 同じ場所の意味を
状態によって切り替えると、**押す前に自分がどのモードにいるかを思い出す必要が生まれる**。
それは「押した場所で何が起きるかが決まる」を、より分かりにくい形で崩す（§6）。

## 4. 削除

- **確認ダイアログを挟む。** 投入は確認なしで即座に通す代わりに、**破壊操作だけは守る**。
- 削除するとエントリと画像の実体の両方が消える（[02](./02-data-model.md) §3）。復元はできない。

## 5. レスポンシブ

Windows / MacBook / iPhone のいずれからも使う。daisyUI + Tailwind のユーティリティで
**同じコンポーネントを幅で出し分ける**（別画面を作らない）。

**狭い幅では操作をアイコンにする。** 規模の表示（§2.1）が増えたことでヘッダ行の文字量が増え、
iPhone の幅では収まらなくなるため。**デスクトップは幅に余裕があるので文字のままでよい**
（アイコンの方が優れているのではなく、狭いから畳むだけ）。

- **ボタンは1つのまま、中身だけを出し分ける。** 幅ごとに別のボタンを並べると、
  DOM 上に同じ操作が二重に存在することになる。
- ⚠ **アイコンだけになるボタンには必ず `aria-label` を付ける。** 文字を隠した時点で、
  そのボタンは**読み上げから名前を失う**。アイコン側は `aria-hidden` にする。
- アイコンは [heroicons](https://heroicons.com/) の outline / 24 から `path` を写して
  自前のコンポーネントにする。**npm パッケージは入れない**（使うのは数個で、依存を1つ増やす
  価値がない。[01](./01-architecture.md) §2 の「共有物が2つ現れた程度で中間パッケージを作らない」と同じ判断）。

## 6. 共有（ログインできない受け手へ渡す）

> データモデルは [02](./02-data-model.md) §6、認証上の位置付けは [04](./04-auth-and-privacy.md) §3.1。

**想定する受け手は LLM のセッション**（Claude Code など）である。貼ったスクリーンショットや
エラーログを、**そのままリンク1本で読ませたい**。

### 選択

**チェックボックスを常に表示する。「選択モード」にしない。**

モードにすれば普段はチェックボックスが見えず、静かになるように思える。**しかし実際には静かにならない。**
モードのトグルボタン自体がどこかに常駐するので、**小さなチェックボックスが 1 個のボタンと
モード状態に置き換わるだけ**であり、画面から要素は消えず**状態だけが増える**。
増えた状態は「いま自分がどのモードにいるか」を利用者に覚えさせる（§3）。

- ヘッダ行の**左端**（作成時刻の前）に置く。カード本体のタップ（＝コピー）とは別の場所である。
- **壊れた行には出さない。** 渡せないものを選ばせない（規模を出さないのと同じ理由。§2.1）。
- 1件以上選ぶと**下部に固定のバー**を出す（`N 件を共有` / `選択解除`）。**0 件のときは何も出さない。**
- **1つのセットは 50 件まで**（[02](./02-data-model.md) §5）。上限に達したら**未選択のものだけ**
  押せなくし、**その理由をバーに書く**。選択済みを外す道は塞がない（塞ぐと選び直せなくなる）。
  ⚠ **画面で止めるだけにしない。** サーバー側の検証は防御として残す。
- **選択は一覧の再読み込みをまたいで保たれる。** 投入や削除のたびに一覧は先頭ページへ戻るが、
  そこで選択を捨てると「貼ってから選ぶ」が成立しなくなる。
  ⚠ **したがって、選択を「いま表示されているもの」で絞り込んではいけない。**
  絞り込むと、続きを読み込んで選んだものが**チェックされたまま共有対象から黙って消え**、
  それでいて上限の枠だけは消費する。**バーの件数と実際に渡すものを必ず一致させる。**
  → 順序は **ULID の降順**で復元できる（辞書順が生成時刻順なので一覧の総順序と一致する。
  [02](./02-data-model.md) §2）。**表示中の配列を見に行く必要がない。**
- **削除されたものは選択から外す。** 残すと、消えたものを含んだまま発行して必ず失敗する。
  ページ外に出ただけのもの（上記）とは違い、これは本当に渡せない。
- ⚠ **タップ領域は見た目より広く取る。** チェックボックスの見た目は小さくてよいが、
  **指で押す的が 16px 程度しかないと iPhone では正確に押せない**（Apple の HIG は最小 44pt）。
  余白を足して的を広げ、**同じ量の負のマージンで打ち消す**——こうすると周りのレイアウトを
  動かさずに的だけが広がる。§5 の「狭いから畳む」とは別の話で、**畳んだ結果として
  押しにくくなってはいけない**。

### 渡すもの

**セット URL は、メンバーの URL を改行で区切った `text/plain` を返す。**

```
https://<origin>/s/<token>/<id>.png
https://<origin>/s/<token>/<id>.txt
```

- **受け手が最もパースしなくて済む形**だから。LLM がリモートの画像を読む実際の経路は
  「**URL を取得してローカルに落とし、それを読む**」であり、この形なら1行ずつ渡すだけで済む。
  書庫形式は展開の手順を、JSON はパースの手間を受け手に作る。
- **メンバー URL には拡張子を付ける。** 付けないと**保存したファイルが何なのか受け手に分からない**。
  拡張子は**保存時にサーバーが判定した `mimeType`** から導出する（申告値ではない。
  [02](./02-data-model.md) §4.1）。
- **人間向けの共有ページは作らない。** 受け手は LLM であり、自分は既にログイン済みの一覧を持っている。
  **無認証で開ける画面を1つ増やすだけ**で、得るものがない。
- **URL は絶対 URL** で書く。オリジンは**設定値から取る**——リクエストの `Host` からは組めない
  （dev では proxy が書き換え、remote では正しいスキームが得られない。[01](./01-architecture.md) §4）。

### 発行

- 発行したら**リンクを画面に表示し、同時にクリップボードへコピーする**（§3 の
  「コピーボタンを探させない」と同じ姿勢）。**自動コピーは補助であり、唯一の経路にしない。**
- **同じ組み合わせでも、発行のたびに新しいトークンを作る。** 使い回すと、
  **前に渡した古いリンクの寿命が知らないうちに延びる。**
- **失効は発行直後のパネルに置く。** 現実に起きる事故は「**渡した直後に、渡し先を間違えたと気づく**」であり、
  そこで切れれば足りる。それ以降は 10 分の期限が処理する。
- **共有中のものを一覧・管理する画面は作らない**（[05](./05-roadmap.md) §未実装）。
  行は残っているので、必要になってから足せる。

⚠ **`await` を挟んだ後のクリップボード書き込みは、Safari では通るとは限らない。**
Safari はクリップボードへの書き込みがユーザー操作と結び付いていることを要求し、
**非同期の隙間が空くとジェスチャーの資格を失いうる**。

そこで **書き込み自体は操作の中で始め、中身だけを後から解決する**（`ClipboardItem` に Promise を渡す）。
発行の応答を待ってから書き込む形にはしない。

- 📌 **実機（iPhone）では、この形で自動コピーが動くことを確認済み**（2026-07-26）。
- 📌 **`await` を挟む形が必ず失敗するわけではない。** 画像のコピー（§3）は実体を取得してから
  書き込んでいるが、同じ実機で通っている。**確実に通る側を選んでいるだけ**であり、
  「await を挟むと必ず拒否される」と読まないこと。
- **どちらにせよ、自動コピーを唯一の経路にしない**（リンクは画面にも出す）。ここは端末とブラウザの
  版に依存する挙動なので、**成否に関わらず利用者が手で取れる状態を保つ**方が確実である。
