## 仕様（2026-07-26 の grill）

### Q1. 溜まる置き場か、流れるバッファか → **溜まる置き場・手動削除**

貼ったものは自動で消さない。失効ジョブもピン留めも作らない。
**「消えて困った」事故を原理的に起こさない**ことを、容量効率より優先した。
個人利用の量なら容量は当分問題にならず、逼迫してから失効を足せる。

### Q2. 扱うデータ → **テキスト + 画像のみ**

原体験（チャット欄への貼り付け）の範囲そのまま。どちらもブラウザでそのままプレビューでき、
**「貼る → 見える」が例外なく成立する**。任意ファイルを入れると、プレビュー不能なものの表示・
ダウンロード UX・MIME の一般化が MVP に入るため見送った。

### Q3. 認証 → **アプリ側の cookie セッション**（`seseraki` と同方式）

前段プロキシの認証に寄せれば実装ゼロだが、**ユーザー名とパスワードで保護された public な場所に
置きたい**という要件があり、また**将来 URL を他人に共有する可能性**を残したい。
「前段を通れる人＝全権限」という構造だと共有だけを開ける余地がないため、アプリ側で持つ。

### Q4. 画像の保存先 → **SeaweedFS（S3 互換）**

`highscore-must-fall` と同じ構成にする。DB に BLOB を入れるとバックアップは dump 一本で済むが、
配信のたびにメモリに乗り DB が肥大する。ローカルボリュームも候補だったが、**既存リポと運用を
揃える**ことを優先した。

### Q5. 投入の単位 → **入力欄を作らない・自動判別・即保存**

**テキストの入力欄を作らない。** 打ち込む場所を用意せず、貼られたものが増えるだけにする。
入力欄が無いので「入力途中の状態」が存在せず、**テキストも画像も即保存**で成立する。
取り出しも**カードをクリックするだけでクリップボードに入る**（コピーボタンを探させない）。
「何かを書く道具」ではなく「受け渡しの中継点」であることを、UI の形で表す。

テキストと画像を1エントリに同居させる（チャット風）案は原体験に近いが、複数添付のモデルと
送信ステップが必須になる。**気軽さを最優先**し、1エントリ = テキストか画像のどちらか一方とした。

これに伴い、**iPhone の投入経路が設計上の争点になる**。iOS Safari は `input` /
`contenteditable` にフォーカスがある時しか `paste` を配らず、「ページに向かって貼り付ける」操作が
OS に存在しない。**ペースト一本では iPhone から投入できない**ため、`navigator.clipboard.read()` を
呼ぶ**「貼り付け」ボタン**を置く。ボタンは入力欄ではないので方針と矛盾しない。

### Q6. 一覧 → **新しい順の時系列のみ**

受け渡し用途では目的のものは大抵一番上にある。検索は溜まって困ってから足す。

### Q7. サムネイル → **作らない**

原寸を CSS で縮小する。画像処理依存と生成失敗時のフォールバック設計を MVP に持ち込まない。
モバイル回線で重いと感じたら後から足す。

### Q8. 構成 → **`packages/{web,server}` の2つ / MySQL 8.4 + Drizzle**

`shared` は作らない（共有するのは API 型だけで、それは Hono RPC が担う）。
`database` パッケージも分けない（テーブル1つの規模で分割の定型句を先に払わない）。
SQLite も候補だったが、**既存リポと手順を揃える**ため MySQL を採った。

### 追加指定

- **フロントは TailwindCSS v4 + daisyUI**（2026-07-26 オーナー指定）。
  個人用ツールに**デザインの意思決定コストを掛けない**ため、daisyUI のコンポーネントに寄せる。

### 実装時の既定値（grill で明示の異論なし）

- テキストはプレーン表示（等幅）。**Markdown レンダリングはしない**（貼ったものがそのまま見えることを優先）。
- 画像は **20MB** まで。
- 一覧は **50件**ずつ。
- 削除は**確認ダイアログあり**（投入は確認なしで通す代わりに、破壊操作だけ守る）。
- エントリ ID は **ULID**（辞書順が生成時刻順なので、一覧の並びとページングが `id` 単独で済む）。
  **認可トークンではない**ので、共有の防壁として使わない（下記）。

## レビューを受けた追加決定（PR #2・2026-07-26）

### 画像形式を allowlist に限る（High 指摘）

**`image/svg+xml` を受け入れると stored XSS になる**（SVG は能動コンテンツで、private データと
同一オリジンで実行されると認証済み API を操作できる）。クライアントの申告した MIME をそのまま
`Content-Type` にして同一オリジンから配信する設計は、この一点で破綻する。

- **PNG / JPEG / GIF / WebP のみ**受け入れ、**サーバーがファイルシグネチャで判定**する。
- 配信に **`X-Content-Type-Options: nosniff`** を付ける。
- 「自分しか貼らないから安全」ではない。**他人からもらった画像を中継するのがこの道具の用途**であり、
  貼る対象の出所は自分の管理外である。

### ログインのレート制限は MVP から外す（Medium 指摘を受けた検討の結論）

**運用上、公開アプリケーションは前段プロキシ（WAF・レート制限あり）の下に置く**（オーナー確認・2026-07-26）。
clip の公開はまだ先で、当面は前段の内側でしか動かさない。

**最も効くのはパスワードの強度**であり、レート制限は本来「弱いパスワードを守る」ための保険にあたる。
`AUTH_PASSWORD` を 32 文字以上のランダム文字列にすることを運用要件とし、
**アプリ側のレート制限は MVP から外す**（オーナー判断・2026-07-26。issue に記録し、後から足す）。

自前実装を検討する過程で次が分かった。**実装するときは自作せず、既存実装に寄せる**
（`better-auth` 内蔵のレート制限・`hono-rate-limiter` 等）:

- **応答を遅らせる（sleep）だけでは並列リクエストに無力。** 遅くなるのは1本あたりの応答だけで、
  検証自体は並列に何度でも走る。
- 検証前にゲートするなら、条件付き UPDATE の **`SET` 句で許可時刻を将来へ進めないと排他にならない**
  （行ロックが解けた後、後続が順に通過する）。
- さらに**リースの所有権検証（fencing token）が要る**。照合が長引いてリースが切れると、
  古い要求が後続の状態を上書きしうる。
- **入力の username でゲート行を絞ると user enumeration になる**（存在しない username だけが
  別経路に落ち、応答差で判別できる）。
- **単一のゲートは、攻撃者に許可時刻ごとに先着され続けると正規ユーザーを無期限に締め出す。**
  指数 backoff に上限を付けても、この可用性問題は解けない。
- **窓ベース**（`better-auth` は `/sign-in` が既定 3 req / 10 秒、`storage: 'database'` で永続化可）
  ならこの締め出し問題は起きにくい。窓が空けば正規ユーザーは通る。

> 認証そのものの定数時間比較（ユーザー名とパスワードを同じ方法で固定長化し、
> **両方を評価してから AND する**）は MVP の要件として残す。早期リターンすると
> ユーザー名の当否が応答時間に出るため（[`../04-auth-and-privacy.md`](../04-auth-and-privacy.md) §2）。

### 二重書き込みは「画面が嘘をつかない方」に倒す（Medium 指摘）

画像の作成と削除は S3 と DB をまたぐため、途中で失敗すると必ず何かが残る。**順序はどちらも
S3 → DB** だが、残る異常は逆になる（作成は orphan な実体、削除は実体を失った行）。
一貫させたのは順序ではなく判断基準の方で、**画面が嘘をつかない側**を選んでいる:

- 作成に失敗したものが一覧に並ぶと、**保存できたと誤解する**（即保存なので確認しない）。
- 削除に失敗したのに一覧から消えると、**消えたと誤解する**（実際にはデータが残っている）。

作成の insert 失敗時は同一リクエスト内で実体を best-effort 削除し、それも失敗したらキーをログに残す
（[`../02-data-model.md`](../02-data-model.md) §3）。

### 一覧の順序は `id`（ULID）単独（Medium 指摘）

`createdAt`（`datetime`）は同値になりうるため、単独では 50件ずつのページ境界が一意にならず、
**同じ行が2ページに出たり、どこにも出なかったりする**。ULID は辞書順が生成時刻順なので、
**`id` の降順単独で「新しい順」が成立し、ページングのカーソルも `id` 単独で足りる**。
主キー索引をそのまま使えるので、並び替えのための索引も要らない。
同一ミリ秒内の順序を一意にするため、ULID は **monotonic な生成器**を使う。

### 共有の防壁は ULID ではなく独立したトークン（Medium 指摘）

ULID は**先頭 48 ビットが生成時刻**で、乱数部の暗号学的安全性も仕様上保証されない。さらに一覧の
順序を `id` 単独にするため **monotonic な生成器**を要求しており、**観測できた ID の近傍は探索しうる**。
「ID が推測しにくいから共有 URL にそのまま使える」は成立しない。

- **ULID の役目は主キーと時系列ページングに限る。** 認可の代わりにしない。
- 将来の他者共有は、clip ID とは**独立した共有トークン**として設計する。十分なエントロピーを持つ
  暗号学的乱数を主体とし、**対象の clip・権限・失効**を保存して検証する
  （[`../04-auth-and-privacy.md`](../04-auth-and-privacy.md) §3）。
- 連番を避ける意味は残る（ID から総件数や作成ペースが読めない）が、それは**防壁ではない**。

## 共有トークン（2026-07-26 の grill・Phase 2-b）

**目的**: Claude Code などの LLM セッションから、貼った画像やテキストを参照させたい。
さらに「複数のうちどれを渡すか」を簡単な操作で制御したい。

採った型は **capability URL × manifest** で、どちらも確立した型である（W3C TAG の
"Good Practices for Capability URLs"）。**URL そのものが資格情報**であり、**1つのハンドルが
N 個のメンバーを指す**。発明した部分は無い。既知の落とし穴（`Referer` 経由の漏洩・履歴やログへの残留・
推測・署名方式では失効できないこと）も、この型に付随するものとして下記で個別に処理している。

### Q1. 選択は認可の境界か、受け渡しの利便か → **認可の境界**

渡していないものには**到達できない**設計にする。対案は「エージェント用の読み取り専用 API トークンを
1本発行し、選択は URL 一覧をコピーするだけの利便機能にする」というもので、こちらの方が実装は軽い
（無認証の経路もテーブルも増えない）。

**それでも境界を選んだのは、LLM のセッションに貼ったものがそのまま transcript に残るからである。**
API トークンは**長期・全 clip 読み取り可**の資格情報で、それを curl のコマンドラインに書けば
シェル履歴と会話ログの両方に残る。後でその会話ログを共有すると、全権の鍵が付いてくる。
共有 URL も transcript に残るが、残るのは**対象が限定され期限で自然に死ぬもの**で、
漏れたときの被害が「貼った数枚」で止まる。

[`../04-auth-and-privacy.md`](../04-auth-and-privacy.md) §1 が既に「**前段を通れる人＝全権限**、
という構造にしない」と書いており、API トークン案はその構造を作り直すことになる。

⚠ 代償は正直に記録しておく。**無認証で開く経路を1本作るので、「全 API がセッションを要求する」
という単純な不変条件が失われる**（§3）。今後 API を足すたびに「共有トークンでも通るのか」を
考える必要が出る。

### Q2. セット URL が返すもの → **改行区切りのメンバー URL 一覧**（`text/plain`）

Claude Code がリモート画像を読む実際の経路は「**URL を curl でローカルに落として Read**」である。
したがって**受け手が最もパースしなくて済む形**を選ぶ。`curl -s <セットURL> | xargs -n1 curl -O`
のようにそのままパイプできる。tar / zip は展開の手順を、JSON はパースの手間を受け手に作る。
情報量が要る場面が来たら `Accept` で出し分けて後から足せる。

- **メンバー URL には拡張子を付ける**（`/s/<token>/<id>.png`）。付けないと `curl -O` が拡張子なしで
  保存し、**受け手が画像だと判別できない**。拡張子は保存済みの `mimeType`（サーバーが判定した値）
  から導出する。
- **人間向けの一覧ページは作らない。** 受け手は LLM であり、自分は既にログイン済みの一覧を持っている。
  **無認証で開ける画面を1つ増やすだけ**で得るものが無い。

### Q3. トークンの持ち方 → **DB に持つ**（`shares` テーブル + 32 バイト乱数）

対案は HMAC 署名トークン（対象 ID と期限をトークン自体に詰める）で、**テーブルを増やさずに済む**。
10 分で死ぬなら失効も期限だけで足りるため、有力な選択肢だった。

**決め手は失効ではなく URL の長さだった。** 署名方式では対象の ULID を全部トークンに詰めるので、
**5 枚選んだ時点でトークンが 300 文字近くなる**。しかも Q2 の形ではメンバー URL にも同じトークンが
載るため、マニフェストが**300 文字の似た行が並んだ壁**になる。受け手にとって読みにくく、
単純にトークンの無駄でもある。DB 方式なら 1 行 80 文字程度に収まる。
**「面倒でない受け渡し」を作るのが目的なので、ここで長い URL を選ぶのは目的に逆行する。**

副次的な利点が2つある。どちらも 10 分の期限では「無くても死なない」が、あると効く:

- **貼り先を間違えたときに即座に切れる**（10 分は「気づいてから何もできない時間」としては長い）。
- **いま何が共有中かを一覧できる。** 署名方式では**原理的に答えられない**。「自分以外に触られない
  ため」を掲げるツールが、外に出ている鍵を数えられないのは穴である。

細部:

- **トークンそのものではなくハッシュ（SHA-256）を保存する。** セッション cookie と同じ扱いで、
  DB が漏れたときに**生きた capability URL がそのまま取り出せる**状態を作らない。
- **`permissions` 列は作らない。** いま権限の種類は1つしかない（そのセットを読む）。
  値が1種類の列は「使わない抽象を先に作らない」（[`../02-data-model.md`](../02-data-model.md) §3）に反する。
  **選ばれた clip の集合そのものが権限である。**

### Q4. 期限付きの状態の置き場所 → **MySQL のみ。Redis / Valkey は入れない**

**ログインゲートで「Redis を使わない」と決めた理由は、ここでは効かない。むしろ逆を指す。**
あちらは「Redis が飛ぶと**制限が外れる**方向に失敗する」（fail-open）ことが理由だった。
共有トークンは真逆で、**状態が消えたらリンクが死ぬ**（fail-closed）。安全な向きに倒れる。

Redis が明確に勝つ点は **TTL が組み込みである**こと（`SET … EX 600`）。DB 方式で必要になる
「期限切れ行の掃除」が丸ごと消える。これは本物の利点である。

それでも MySQL を選んだのは、**この機能の大きさに対して払うものが多いから**:

- compose にサービス追加（dev と remote 両方）・クライアント依存・接続失敗の経路。
- **真実の在り処が2つになる**（何が共有中かは Redis、何が clip かは MySQL）。
- 本番の Redis が他プロジェクトと同居なら**キー名前空間**が要り、`maxmemory-policy` が LRU なら
  **期限前に消えうる**（fail-closed なので危険ではないが、原因の分かりにくい「たまに切れる」になる）。

対して MySQL 側の負債は「**新しい共有を作るときに期限切れ行を消す**」1行で、cron も要らない。
同時に生きる行はせいぜい 1〜3 個である。

⚠ **判断を変える条件**: Redis の第2の用途が見えたら、この機能はその最初の使い道として妥当になる。
現状 clip には無い（セッションは HMAC の stateless でサーバー状態を持たず、レート制限は
MySQL と決めて MVP 外）。**いま入れると 1〜3 個のキーのためだけに 1 サービス動かすことになる。**

### Q5. テキストも共有できるか → **できる**

当初の意図は画像だったが、UI にチェックボックスを置くと「なぜこのカードは選べないのか」が必ず出る。
そして用途は端末間クリップボードなので、**LLM に渡したいものは「スクショ + エラーログ」のような組**に
なるのが自然である。画像だけだと**テキストは別途貼り直すことになり、それはまさに消そうとしている
「面倒」そのもの**になる。

⚠ ただし**無条件では通せない**。共有経路は**無認証かつ同一オリジン**なので、利用者のテキストを
そのまま返すと **HTML を貼った clip がアプリのオリジンでレンダリングされうる**。
[`../02-data-model.md`](../02-data-model.md) §4.1 が SVG を allowlist から外したのと**同じ stored XSS**
であり、無認証な分そちらより条件が緩い。次を必須とする:

- `Content-Type: text/plain; charset=utf-8` を固定で返す。
- **`X-Content-Type-Options: nosniff`**（画像配信で既に使っている。§4.2）。
- **`Content-Disposition: attachment`**。curl の挙動は変わらず、**ブラウザでの inline 描画だけが消える**。

### Q6. 選択 UI → **常時表示のチェックボックス**（モードにしない）

対案は「選択モードのトグル」で、普段はチェックボックスが見えない分だけ静かに見える。
**しかし実際には静かにならない。** モードのトグルボタン自体がどこかに常駐するので、
**N 個の小さなチェックボックスが 1 個のボタン + モード状態に置き換わるだけ**であり、
画面から要素は消えず**状態だけが増える**。増えた状態は「いま自分がどのモードにいるか」を
利用者に覚えさせる。[`../03-ux.md`](../03-ux.md) §3 が守ろうとしているのは
**押した場所で何が起きるかが決まる**ことなので、モードはその精神から遠ざかる。

- ヘッダ行の**左端**（時刻の前）にチェックボックス。**壊れた行には出さない**
  （規模の表示と同じ理由。渡せないものを選ばせない）。
- 1件以上選ぶと**下部に固定バー**（`N 件を共有` / `選択解除`）。0 件なら何も出さない。
- 発行したらリンクを表示し、**同時にクリップボードへ自動コピー**する（§3 の
  「コピーボタンを探させない」と同じ姿勢）。

⚠ **iPhone での懸念**: `await`（発行の POST）を挟んだ後の `navigator.clipboard.writeText()` は、
Safari で**通るとは限らない**。書き込みがユーザー操作と結び付いていることを要求し、
**非同期の隙間が空くとジェスチャーの資格を失いうる**ため。
**`ClipboardItem` に Promise を渡す**形にすれば、書き込み自体はジェスチャー内で始まり
中身だけ後から解決する。**どちらにせよリンクは画面にも表示し、自動コピーを唯一の経路にしない。**

> **訂正（2026-07-26・実機で確認）**: ここに当初「**既存のカードのコピーは同期的なのでまだ
> 踏んでいない**」と書いたが、**事実ではなかった**。画像のコピー（`copyImage`）は実体を
> `await` で取得してから書き込んでおり、まさにこのパターンである。
> そして **iPhone の実機では、画像のコピーも共有リンクの自動コピーも通った。**
>
> つまり「**Safari は await を挟んだ書き込みを必ず拒否する**」という当初の断定は**強すぎた**。
> 実装（`ClipboardItem` に Promise を渡す）は**確実に通る側を選んでいるだけ**であり、変更は要らない。
> **端末とブラウザの版に依存する挙動なので、成否に関わらず手で取れる状態を保つ**という
> 結論の方が本質だった。

### Q7. 前段プロキシ → **共有パスだけ、前段の認証を通さない**

remote では前段プロキシ（認証付き）の内側で動かしている。**アプリ側を無認証にしても、
それだけでは受け手は届かない**——前段で止まるからである。

対案は前段が発行する機械向けの資格情報を受け手に持たせる案だが、**Q1 の判断を丸ごと打ち消す**。
長期資格情報を LLM の環境に置かないために共有トークンを選んだのに、それを持ち込むことになる。
取得コマンドもシークレットヘッダ付きの長い行になり、「面倒でない受け渡し」でもなくなる。

前段を1枚剥がすのは一見「守りを弱める」ように見えるが、
**[`../04-auth-and-privacy.md`](../04-auth-and-privacy.md) §1 が最初から宣言していたことの実行**である
（前段があってもなくても、アプリ単体で保護が成立する）。共有トークンはそれ自体が認可の境界として
設計されている。**前段を重ねないと不安なら、それは共有トークンの設計を信用していないということで、
そのときは設計の方を直すべきである。**

条件:

1. **素通しにする対象は共有パスちょうどに限る。** ここを広げると**アプリ全体が無認証で公開される**。
   設定ミスの被害が最大級なので、**設定後に必ず否定側を確認する**——本体・API・
   **dev サーバーがソースを配信する経路**が、今も認証を要求すること。
   肯定側（共有パスが通ること）だけを見ると、広すぎる設定に気づけない。
2. **マニフェストもメンバーも URL を `/s/` 配下に揃える。** 素通しの範囲を1本で済ませるため。
   `/api/clips/:id/blob` に共有トークンを受け付ける形にすると、**認証必須のはずのパスに
   無認証の抜け道が生える**。**共有は専用パスに隔離する。**

一般化できる学び（製品に依存しない形で残す）:

- **「誰でも許可」と「認証しない」は別物である。** 前者は**まず認証させてから**全員を通すので、
  受け手はログイン画面に当たる。**認証そのものを外す設定でなければ意味がない。**
  ここは取り違えやすく、実際に一度踏んだ。
- **トークンをクエリ文字列に載せなくてよかった。** 前段の経路指定はクエリを見ないことがあり、
  その場合**共有経路だけを切り出すことが原理的にできない**。パスに載せる判断が結果的に効いた。
- ⚠ **素通しにした経路は、前段の監査ログに残らないことがある。** 「誰がいつ叩いたか」は
  アプリ側のログだけが手掛かりになる（Q8 の寿命が防御の一部である理由でもある）。
- 📌 **実装要件**: dev では Vite が `/api` しかサーバーへ転送しないため、**`/s` を転送設定に足さないと
  共有パスがサーバーに届かない**（足すまで SPA の `index.html` が静かに返る）。

> **前段の製品名・認証方式・ポリシーの具体・実測結果は、公開リポには書かない**
> （[`../../AGENTS.md`](../../AGENTS.md) 公開リポジトリ方針）。手順と検証コマンドは
> `.claude-personal/` に置いてある。

### Q8. 期限と失効 → **10 分固定・失効は発行直後のパネルのみ**

想定する使い方は「発行 → LLM に貼る → LLM が読む」で**秒〜分で終わる**。期限を UI で選ばせると
**毎回どうでもいい判断を強いる**だけなので固定し、`limits.ts` の定数に置く（上限値を web と共有する
既存の手口と同じ）。短すぎたと分かったら1行変える。

**発行のたびに新しいトークンを作り、同じ集合でも使い回さない。** 使い回すと**前に貼った古いリンクの
寿命が知らないうちに延びる**。

管理画面（共有中の一覧・失効）は**作らない**。現実に起きる事故は「**貼った直後に、貼り先を間違えたと
気づく**」であり、パネルが開いている間に切れれば足りる。数十分後に思い出す事故は 10 分の期限が
処理している。**これは Q3 で挙げた利点の片方しか実現していないが、Q3 で署名方式を退けたことと
矛盾しない**——署名方式では**原理的に答えられない**のに対し、DB 方式では**行が既にあり、
画面を作れば明日にでも答えられる**。能力は持っており、画面をまだ作っていないだけである。

### Q9. マニフェストに書く絶対 URL のオリジン → **設定値だけから取る**

対案は常にリクエストの `Host` / `X-Forwarded-Proto` から組む案で、**「マニフェストを取りに来られた
ホストは、その受け手にとって到達可能だと実証済み」**という本物の論拠がある。`PUBLIC_ORIGIN` が
誤設定されていれば、こちらは**受け手が到達できない URL を静かに吐く**。

それでも env を選んだのは**スキームのため**である。前段は平文でコンテナに繋ぐので、リモートでも
サーバーが見るのは `http` であり、正しい `https://` を組むには **`X-Forwarded-Proto` を信じる**
必要がある。[`../04-auth-and-privacy.md`](../04-auth-and-privacy.md) §1 が**前段を前提にしない**と
宣言している以上、ここで前段のヘッダ設定に正しさを預けるのは方針とちぐはぐである。
リモートでは `.env.remote` に確実に設定されている（無いと `vite.config.ts` が成立しない）。
**設定済みの正しい値があるのに推測に頼る理由が無い。**

⚠ **当初は「未設定ならリクエストの `Host` から組む」としていたが、それは誤りだった**
（レビューで判明。2026-07-26）。**この構成では Host から組めない**:

- **dev では Vite の proxy が `changeOrigin: true` で Host を書き換える。** サーバーが見るのは
  利用者のオリジンではなく転送先（`server:4000`）で、そこから組んだ URL は**ホストに公開していない
  コンテナを指す**。ブラウザからも受け手からも届かない。
- **remote では正しいスキームが得られない**（上記のとおり）。

つまり **サーバーは自分の公開オリジンを発見できない。設定として受け取るしかない。**
未設定時は推測せず、**ローカル dev の固定既定値**（`http://localhost:5173` = `WEB_BIND` の既定に対応）を
使う。**`Host` にも `X-Forwarded-*` にもフォールバックしない。**

📌 現状**サーバーのコードは `PUBLIC_ORIGIN` を一度も読んでいない**（読み手は `vite.config.ts` だけ）。
compose からは既に渡っているので、これが**サーバー側で最初の使い道**になる。

### Q10. スキーマ → **1テーブル・対象 ID は JSON 列**

対案は `shares` + `shareClips` の正規化だが、中間テーブルが効くのは「**この clip を含む共有はどれか**」を
逆引きしたいときである。**その問いを立てる場面を1つも作っていない**（削除は共有を無視して通す）。
逆引きしない中間テーブルは「使わない抽象を先に作らない」に真正面から当たる。

しかも JSON 列の帰結が、合意した挙動とそのまま噛み合う。**外部キーを張れないので clip が消えても
ID は残り**、参照時に現存する clip だけを引けば**消えたものは自然にマニフェストから落ち、
メンバー URL は 404 になる**。整合のための特別な処理が要らない。

| 列 | 型 | 理由 |
|---|---|---|
| `id` | `char(26)` | ULID・主キー。`clips` と揃え、将来の一覧画面の順序を §2 と同じ理屈で確保する |
| `tokenHash` | `char(64)` unique | **トークンそのものは保存しない**。SHA-256 の hex |
| `clipIds` | `json` | 対象 ID の配列。**構造の保証はアプリ層の zod**（§2 と同じ分担） |
| `expiresAt` | `datetime` | 10 分後 |
| `createdAt` | `datetime` | `clips` と揃える |

**`revokedAt` は持たず、失効は行の削除**とする。10 分で消える行に履歴を残す意味が無く、
`expiresAt` の判定に条件が1つ増えるだけである。

### 形（上記から決まるもの）

```
GET    /s/<token>            → メンバー URL の改行区切り一覧（無認証）
GET    /s/<token>/<id>.png   → 実体（無認証）
POST   /api/shares           → 発行（要セッション）。期限切れ行の掃除もここで行う
DELETE /api/shares/:id       → 失効（要セッション）。行を削除する
```

配信ヘッダは**テキストも画像も**: サーバー判定の `Content-Type`（テキストは
`text/plain; charset=utf-8` 固定）・`X-Content-Type-Options: nosniff`・`Content-Disposition: attachment`。

帰結（判断ではなく、上から自動的に決まるもの）:

- セット内の clip を削除しても止めない。マニフェストから落ち、メンバー URL は 404。
  [`../03-ux.md`](../03-ux.md) §4 の「削除は破壊操作」を共有が上書きしない。
- 壊れた行は選べない。共有中に壊れたら 404。
- 1セットの上限は **50 件**（一覧のページサイズに揃える）。
- `/s/*` は **GET のみ**。読み取り専用。
- 失効の宛先は `id`。**生のトークンを再送しない。**

### やらないこと・先送り

- **共有中の一覧・管理画面**（能力は持つが画面は作らない。Q8）。
- **他者への人間向け共有**（Q2 で一覧ページを作らないと決めている）。
- **前段プロキシ側の設定そのもの**はリポジトリ外の運用作業。PRD には姿勢だけを書き、
  **製品名・認証方式・ポリシーの具体・ホスト名・実測結果**は `.claude-personal/` に置く。
