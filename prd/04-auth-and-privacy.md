# 04. 認証とプライバシー

> 本章の内容は**全て計画**（実装は未着手）。

本アプリは**個人用・シングルユーザー**である。認証は「自分以外に触られないため」の最小限であり、
マルチユーザー・owner 分離は持たない（[02](./02-data-model.md)）。

## 1. 前段プロキシに依存しない

開発時は前段プロキシ（認証付き）越しに使うが、**アプリはそれを前提にしない**。
前段があってもなくても、**アプリ単体で保護が成立する**ように作る。

理由は2つある:

- **公開された場所に置きたい。** 前段の認証があるからアプリ側は素通し、という設計だと、
  置き場所を変えた瞬間に丸裸になる。
- **将来 URL を他人に渡す可能性がある**（[05](./05-roadmap.md) §未実装）。そのとき「前段を通れる人＝
  全権限」という構造だと、共有だけを開ける余地がない。

## 2. Web の認証（cookie セッション）

`seseraki` と同方式を採る（運用と踏んだ罠を共有できるため）。

- ログインフォーム（`/login`）→ `POST /api/auth/login` → **署名付き cookie**（`clip_session`）を発行。
- 認証情報は `AUTH_USERNAME` + `AUTH_PASSWORD`（`.env.server` を秘密として運用）。

### 照合の方法

**定数時間比較を行うが、`crypto.timingSafeEqual` に文字列を Buffer 化してそのまま渡さない。**

- この API は**長さの異なる Buffer を渡すと `false` ではなく例外を投げる**。素直に実装すると、
  **長さ違いの誤入力（最も普通の打ち間違い）が認証失敗ではなく 500 になる**。
  そのリクエストは「認証失敗」の経路を通らないため、**失敗記録にも backoff にも掛からない**。
  総当たりの側から見れば、**長さを変えるだけで制限を回避できる**ことになる。
- **入力値と期待値を同じハッシュ（SHA-256）で固定長にしてから `timingSafeEqual` に渡す。**
  長さに関わらず比較でき、例外の経路そのものが無くなる。
- **どの理由で失敗しても同じ「認証失敗」の経路を通す。** ユーザー名が違う場合とパスワードが
  違う場合で、応答内容も所要時間も区別しない。失敗記録と backoff は必ずこの経路で適用する。
- cookie は **HMAC 署名 + 発行時刻埋め込みで stateless**。**30 日固定有効期限**（スライディングなし）。
  署名鍵は `SESSION_SECRET`。
- cookie 属性: `HttpOnly; SameSite=Lax`、本番は `Secure`、**`Path=/` 固定**（`COOKIE_SECURE` env で切替）。
  web は origin 直下、API は origin 直下の `/api` に配信する前提（[01](./01-architecture.md) §5）。

### 総当たりへの耐性（多層で守る）

`timingSafeEqual`（定数時間比較）はタイミングからの情報漏洩を防ぐだけで、**総当たりは一切防がない**。
ログイン API は公開される唯一の認証境界なので、別に手当てが要る。**2層に分けて受け持たせる。**

| 層 | 担当 | 守れるもの |
|---|---|---|
| **前段プロキシ**（WAF / レート制限） | 運用側 | **高頻度の試行**。送信元 IP・国・挙動での遮断はここが最も得意 |
| **アプリ**（本 PRD の要件） | 実装 | **低速な試行**。前段の閾値に掛からない毎分数回のペースは通ってしまう |

**アプリ側の要件は、アカウント単位の失敗回数に応じた遅延（backoff）のみとする。**

- 連続失敗が増えるほど応答を遅らせる。**完全にロックはしない**（正規の自分が締め出されるため。
  正しい資格情報なら、遅延は掛かっても必ず通る）。
- 失敗の記録を残し、**異常な回数の失敗に気づけるようにする**（監視の初歩）。

### 送信元単位の制限をアプリ側に持たない理由

IP 単位のレート制限は、**送信元を正しく識別できること**が前提になる。リバースプロキシの背後では
全リクエストがプロキシの IP から来ているように見えるため、`X-Forwarded-For` を信頼する
proxy hop 数とともに解釈する必要がある。**この設定を間違えると、詐称されたヘッダで制限を
無効化されるか、逆に全員が同一送信元と見なされて誰も入れなくなる。**

前段プロキシが IP 単位の制限を最も正確に行える位置にいる以上、**その責務は前段に委ね、
アプリは送信元の識別に一切依存しない設計にする**（アカウント単位なら識別が不要）。

> これは「前段に依存する」ことではない。**前段が無い場所に置いてもアプリ側の backoff は効く**。
> 前段があれば、高頻度の試行がアプリに届く前に落ちるというだけである（[§1](#1-前段プロキシに依存しない)）。

将来アプリ側に IP 単位の制限を足すときは、**信頼する hop 数を設定で明示し、明示的に有効化した
ときだけ転送ヘッダを参照する**こと。配置ごとの実際の値は公開せず `.claude-personal/` に置く。

### 認証 API

| Method | Path | 説明 |
|---|---|---|
| GET | `/api/auth/me` | ログイン状態確認。未ログインは 401 |
| POST | `/api/auth/login` | body: `{ username, password }`。成功で署名付き cookie 発行 |
| POST | `/api/auth/logout` | cookie を破棄 |

`/login` 以外は web のルートガードで `/api/auth/me` を叩き、未ログインなら
`/login?redirect=<元の URL>` へリダイレクトする。

## 3. ルート保護

**`/api/auth/*` を除く全ての API がセッションを要求する。**

| 対象 | 認証 |
|---|---|
| `/api/clips`（一覧・作成・削除） | 必要 |
| **`/api/clips/:id/blob`（画像の取得）** | **必要** |
| `/api/auth/login`・`/api/auth/me` | 不要（`me` は未ログインなら 401 を返す） |

**画像の取得にも認証を要求する**ことを明記しておく。ここを「画像くらいは素通しでいい」と
緩めると、[§1](#1-前段プロキシに依存しない) の前提が崩れる。将来の他者共有は、
**この原則の明示的な例外**として設計する（署名付きの共有トークンを別に持つ）。

## 4. プライバシーと公開配置の前提

- **シングルユーザー・private データのみ。** 貼ったものを自分だけが見る。
- 公開配置の前提: HTTPS / シークレット管理（`.env*` はコミットしない）/ 同一オリジン配信。
  同一オリジンのため CORS は原則不要。
- **本番/開発の具体情報（ドメイン・TLS・接続先・リバースプロキシ・バインドポート・シークレット）は
  公開リポに含めない。** PRD は姿勢のみ記述し、具体はローカルの `.claude-personal/` に置く。
- **貼り付けた実データを公開リポに持ち込まない。** 動作確認のスクリーンショットを PR に添える場合は、
  差し支えのないダミーを貼って撮る。
