# 04. 認証とプライバシー

> **実装済み**: cookie セッション認証（§2 の照合方法・cookie 属性）/ 認証 API / `/login` と
> web のルートガード（Phase 1-3）/ **§3 のルート保護**（`/api/clips` と画像の取得に
> `sessionRequired` を適用。Phase 1-4）。
> **§3.1 の共有トークン**（`shares` / 発行・失効 API / 無認証の `/s/*`。Phase 2）。
> **レート制限はアプリ側に持たず、前段プロキシに委ねる**（§2・issue #3。前段が満たすべき条件は
> [06](./06-deployment.md) §5）。

本アプリは**個人用・シングルユーザー**である。認証は「自分以外に触られないため」の最小限であり、
マルチユーザー・owner 分離は持たない（[02](./02-data-model.md)）。

## 1. 前段プロキシに依存しない

開発時は前段プロキシ（認証付き）越しに使うが、**アプリはそれを前提にしない**。
前段があってもなくても、**アプリ単体で保護が成立する**ように作る。

理由は2つある:

- **公開された場所に置きたい。** 前段の認証があるからアプリ側は素通し、という設計だと、
  置き場所を変えた瞬間に丸裸になる。
- **将来 URL を他人に渡す可能性がある**（[05](./05-roadmap.md) §未実装）。そのとき「前段を通れる人＝
  全権限」という構造だと、共有だけを開ける余地がない。

## 2. Web の認証（cookie セッション）

`seseraki` と同方式を採る（運用と踏んだ罠を共有できるため）。

- ログインフォーム（`/login`）→ `POST /api/auth/login` → **署名付き cookie**（`clip_session`）を発行。
- 認証情報は `AUTH_USERNAME` + `AUTH_PASSWORD`（`.env.server` を秘密として運用）。

### 照合の方法

**定数時間比較を行うが、`crypto.timingSafeEqual` に文字列を Buffer 化してそのまま渡さない。**

- この API は**長さの異なる Buffer を渡すと `false` ではなく例外を投げる**。素直に実装すると、
  **長さ違いの誤入力（最も普通の打ち間違い）が認証失敗ではなく 500 になる**。
  正しい応答を返せないうえ、**応答の違いから「長さが合っているか」を判別できてしまう**。
- **入力値と期待値を同じハッシュ（SHA-256）で固定長にしてから `timingSafeEqual` に渡す。**
  長さに関わらず比較でき、例外の経路そのものが無くなる。
- **ユーザー名とパスワードを同じ方法で比較する。** どちらも固定長化して `timingSafeEqual` に掛け、
  **両方を必ず評価してから結果を AND する**（片方が違った時点で早期リターンしない。
  そこで返すと、ユーザー名が合っているかどうかが応答時間に出る）。
- **どの理由で失敗しても同じ `401` を返す。** ユーザー名が違う場合・パスワードが違う場合・
  長さが違う場合のいずれも、応答内容も所要時間も区別しない。
- cookie は **HMAC 署名 + 発行時刻埋め込みで stateless**。**30 日固定有効期限**（スライディングなし）。
  署名鍵は `SESSION_SECRET`。
- cookie 属性: `HttpOnly; SameSite=Lax`、本番は `Secure`、**`Path=/` 固定**（`COOKIE_SECURE` env で切替）。
  web は origin 直下、API は origin 直下の `/api` に配信する前提（[01](./01-architecture.md) §5）。

### 入力の上限（MVP 要件）

**ログイン API は未認証で叩ける唯一の口なので、単一リクエストの資源上限をアプリ側で強制する。**

- **body に小さなバイト上限**（4KB 程度）を掛け、超過は `413` で落とす。
- `username` / `password` にも**最大文字数**を設ける。

試行**回数**の制限（レート制限）は MVP 外だが（下記・issue #3）、**1本あたりが際限なく大きくなること**は
別の問題として防ぐ。巨大な JSON を送りつけられると、body の保持と解析、そして照合時の
ハッシュ計算でメモリとイベントループを占有できる。**前段プロキシの設定だけに頼らない**（[§1](#1-前段プロキシに依存しない)）。

### 総当たりへの耐性（前段に委ねる）

`timingSafeEqual`（定数時間比較）はタイミングからの情報漏洩を防ぐだけで、**総当たりは一切防がない**。
これへの手当ては次のように分担する。

| 層 | 担当 | 扱い |
|---|---|---|
| **パスワードの強度** | 運用 | **必須**。`AUTH_PASSWORD` は 32 文字以上のランダム文字列にする |
| **前段プロキシの認証** | 運用 | **前提とする**。ログインの口に**そもそも到達させない**（[06](./06-deployment.md) §5 の要件 2・3） |
| **前段プロキシのレート制限** | 運用 | **前提とする**。無認証で開いている経路（`/s`）と、認証の口を守る（[06](./06-deployment.md) §5 の要件 4・5） |
| **アプリ側のレート制限** | 実装 | **作らない**（[05](./05-roadmap.md) §未実装） |

**前段が担うものを「WAF」と一括りにしない。** 認証とレート制限は別の層であり、
効き方も違う——**認証は到達そのものを断ち**、レート制限は**到達する経路（`/s`）の消費を抑える**。
どちらを当てにしているのかを混ぜると、片方しか無い場所へ置いたときに気づけない。

**最も効くのはパスワードの強度である。** 32 文字以上のランダム文字列なら、毎秒百万回試行されても
総当たりは終わらない。レート制限は本来「弱いパスワードを守る」ための仕組みであり、
**強いパスワードを使う限り、その上に積む保険**にあたる。

#### アプリ側のレート制限を作らない理由

- **前段プロキシ（認証付き）の内側でしか動かさない。** これは開発環境だけの話ではなく、
  **本番も同じ前提で配置する**（[06](./06-deployment.md) §5）。
- **自前で正しく作るのは難しい。** 検討の過程で、応答を遅らせるだけでは並列試行を止められないこと、
  条件付き UPDATE には所有権の検証（fencing）が要ること、単一のゲートは攻撃者に先着され続けると
  正規ユーザーを締め出すことが分かっている（[`_grilling/decisions.md`](./_grilling/decisions.md)）。
  **これは分散ロックの設計であり、個人用ツールの MVP が抱える複雑さではない。**
- **後から足せる。** 実装するときは自作せず、**既存実装に寄せる**（`better-auth` 内蔵の
  レート制限や `hono-rate-limiter` 等）。検討結果と踏む罠は **issue #3** に残してある。

> ⚠ **前段プロキシの無い場所に公開する前に、必ずレート制限を実装すること。**
> [§1](#1-前段プロキシに依存しない) の「前段に依存しない」は**認証そのもの**についての話であり、
> **総当たり耐性は前段に依存している**。ここだけは前提が異なる。
>
> **本番へ出すこと自体はこの条件に当たらない。** 本番も前段プロキシの内側に置くためである
> （[06](./06-deployment.md) §5）。当たるのは**前段を持たない場所へ移すとき**であり、
> そのとき必要なのは「公開したかどうか」ではなく「**[06](./06-deployment.md) §5 の要件 2〜5 が
> 満たされているか**」で判断する。

### 認証 API

| Method | Path | 説明 |
|---|---|---|
| GET | `/api/auth/me` | ログイン状態確認。未ログインは 401 |
| POST | `/api/auth/login` | body: `{ username, password }`。成功で署名付き cookie 発行 |
| POST | `/api/auth/logout` | cookie を破棄 |

`/login` 以外は web のルートガードで `/api/auth/me` を叩き、未ログインなら
`/login?redirect=<元の URL>` へリダイレクトする。

## 3. ルート保護

**`/api/*` は、`/api/auth/*` を除く全てがセッションを要求する。**

| 対象 | 認証 |
|---|---|
| `/api/clips`（一覧・作成・削除） | 必要 |
| **`/api/clips/:id/blob`（画像の取得）** | **必要** |
| `/api/shares`（共有の発行・失効。§3.1） | 必要 |
| **`/s/*`（共有トークンでの取得。§3.1）** | **不要。この原則の唯一の例外** |
| `/api/auth/login`・`/api/auth/me` | 不要（`me` は未ログインなら 401 を返す） |
| `/api/health`（起動確認） | 不要。**状態を持たず成否だけを返す**ので、認証を掛けるとサービスの疎通確認ができなくなる |

**画像の取得にも認証を要求する**ことを明記しておく。ここを「画像くらいは素通しでいい」と
緩めると、[§1](#1-前段プロキシに依存しない) の前提が崩れる。

### 3.1 共有トークン（唯一の例外）

**目的は、ログインできない受け手——具体的には LLM のセッション——へ、選んだエントリだけを渡すこと。**
選択は利便のための機能ではなく、**認可の範囲そのもの**である。渡していないものには到達できない。

**なぜセッションを配らずトークンを配るのか。** 受け手に長期の資格情報（API トークンやセッション）を
渡すと、それは**会話ログとシェル履歴の両方に残る**。後でそのログを共有すると、**全ての clip を
読める鍵が付いてくる**。共有 URL も同じく残るが、残るのは**対象が限定され期限で自然に死ぬもの**であり、
漏れたときの被害が「渡した数件」で止まる。[§1](#1-前段プロキシに依存しない) の
「**前段を通れる人＝全権限、という構造にしない**」を、受け手についても貫くということである。

| Method | Path | 認証 | 説明 |
|---|---|---|---|
| POST | `/api/shares` | 必要 | 選んだ clip からトークンを発行。**期限切れ行の掃除もここで行う** |
| DELETE | `/api/shares/:id` | 必要 | 失効（行を削除）。**宛先は `id`。生のトークンを再送しない** |
| GET | `/s/<token>` | 不要 | メンバー URL の一覧（[03](./03-ux.md) §6） |
| GET | `/s/<token>/<id>.<ext>` | 不要 | 実体 |

満たす条件:

- **clip の `id`（ULID）を防壁にしない。** ULID は認可トークンではなく、時刻由来かつ単調増加なので
  近傍の探索を許す（[02](./02-data-model.md) §2）。`id` はトークンで開いた**後**の宛先にしか現れない。
- **トークンは 32 バイトの暗号学的乱数**（base64url）。DB には **SHA-256 のみ**を保存する
  （[02](./02-data-model.md) §6）。
- **トークンで開けるのは、そのトークンが指す対象だけ。** 一覧にも他の clip にも届かない。
- **`/s/*` は GET のみ。** 読み取り専用で、投入も削除もできない。
- **寿命は 10 分固定**（[02](./02-data-model.md) §5）。失効の主役は期限であり、取り消しは補助。

#### 共有は専用パスに隔離する

**`/api/clips/:id/blob` に共有トークンも受け付ける、という形にしない。**
認証必須のはずのパスに無認証の抜け道が生え、**そのパスを見ただけでは保護の有無が判断できなくなる**。
`/s/` 配下に分けておけば、**パスを見れば認証の要否が分かる**。

前段プロキシを使う配置では、**この1本のプレフィックスだけを素通しにすればよい**という運用上の利点もある
（[§4](#4-プライバシーと公開配置の前提)）。

#### 無認証で返すものへのヘッダ

`/s/*` は**無認証かつアプリと同一オリジン**なので、返す中身がそのままアプリのオリジンで解釈されうる。
[02](./02-data-model.md) §4.1 が SVG を allowlist から外したのと**同じ stored XSS** であり、
無認証な分そちらより条件が緩い。次を必須とする:

- **`Content-Type` はサーバーが持っている値のみ。** 画像は保存時に判定した `mimeType`、
  **テキストは `text/plain; charset=utf-8` に固定**する（HTML を貼った clip を HTML として返さない）。
- **`X-Content-Type-Options: nosniff`**（[02](./02-data-model.md) §4.2 と同じ）。
- **`Content-Disposition: attachment`**。**ブラウザでの inline 描画だけが消え、
  受け手（`curl`）の挙動は変わらない**ので、払う価値のあるコストである。
- **`Cache-Control: no-store`**（マニフェストと実体の**両方**に付ける）。

#### なぜ `no-store` が失効の一部なのか

**キャッシュを止めないと、期限も取り消しも成立しない。** 一度成功した応答が
ブラウザや中間キャッシュに残ると、**サーバーに問い合わせずにそのまま返される**。
その状態では、`expiresAt` を過ぎても行を削除しても、**同じ URL から中身が取り出せてしまう。**

これは「認証必須の経路と違い、共有経路には**セッションという再検証の機会が無い**」ことから来る差である。
`/api/*` は cookie が失効すれば次の要求で 401 になるが、**`/s/*` の失効はサーバー側の状態にしか無い**。
**サーバーに毎回訊かせること自体が、失効の仕組みの一部**になる。

⚠ **`no-cache` では足りない。** `no-cache` は「保存はするが、使う前に再検証する」であり、
保存自体は許す。ここで止めたいのは**保存**なので `no-store` を使う。

⚠ **認証必須の `/api/clips/:id/blob` は、逆に `no-cache` を使う**（[02](./02-data-model.md) §4.2）。
**同じ画像を配る2つの経路が、違うヘッダを持つ。**「揃えよう」として一方に寄せないこと:

- `/s/*` を `no-cache` に緩めると、**上に書いた失効そのものが壊れる**。
- `/api/*` を `no-store` に寄せると、失効の役はセッションが担っているので**何も守れないまま**、
  一覧を開くたびに全件を取り直すだけになる（それが実際に遅かった）。

#### トークンをログに書かない

**トークンは URL のパスに載る。** 何もしなければ、既存のリクエストロガーが
`/s/<token>` を**そのまま標準出力へ書く**。それは **DB にハッシュしか置かない防御を、
ログ側から迂回できる**ということである——ログを読めれば、生きている 10 分の間、
有効な共有 URL をそのまま組み立てられる。

- **`/s/*` のリクエストログでは、トークンの部分を固定文字列に置き換える**（例: `/s/<token>`）。
  **パスをそのまま出力するロガーを、この経路に素通しで適用しない。**
- 監査に残す価値があるのは **`shares.id`・成否・時刻**であって、トークンそのものではない。
  `id` は認可に使えないので、ログに残っても capability にならない。
- **エラーメッセージやスタックトレースにも載せない。**
- ⚠ **前段プロキシのアクセスログは、こちらで制御できない**（[§4](#4-プライバシーと公開配置の前提)）。
  そこに URL が残りうることは前提として受け入れ、**寿命を短く保つこと**で被害の窓を閉じる。
  これは「10 分固定」が単なる利便の設定ではなく、**防御の一部**である理由でもある。

## 4. プライバシーと公開配置の前提

- **シングルユーザー・private データのみ。** 貼ったものを自分だけが見る。
- 公開配置の前提: HTTPS / シークレット管理（`.env*` はコミットしない）/ 同一オリジン配信。
  同一オリジンのため CORS は原則不要。
- **前段プロキシ（認証付き）の内側に置く場合、`/s/*` だけはその認証を通さない設定が要る**
  （[§3.1](#31-共有トークン唯一の例外)）。受け手はそもそも前段を通れないので、ここを塞いだままでは
  共有が成立しない。**素通しにするのは `/s/` プレフィックスちょうどに限る**——広げると
  アプリ全体が無認証で公開される。**設定したら、本体・API・開発サーバーが配信する経路が
  今も認証を要求することを実測で確かめる**（否定側の確認をしないと、広すぎる設定に気づけない）。
  **前段が満たすべき条件と、確かめる項目は [06](./06-deployment.md) §5・§6 にまとめてある。**
  ⚠ この経路は前段のアクセスログに残らないことがある。**誰がいつ叩いたかはアプリ側のログだけが手掛かり**になる。
  **前段の具体（製品名・ドメイン・ポリシー設定）はここに書かない**（§下記の秘匿方針）。
- **本番/開発の具体情報（ドメイン・TLS・接続先・リバースプロキシ・バインドポート・シークレット）は
  公開リポに含めない。** PRD は姿勢のみ記述し、具体はローカルの `.claude-personal/` に置く。
- **貼り付けた実データを公開リポに持ち込まない。** 動作確認のスクリーンショットを PR に添える場合は、
  差し支えのないダミーを貼って撮る。
