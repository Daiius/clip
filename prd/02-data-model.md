# 02. データモデル

> **実装済み**: `clips` テーブル（§2）/ ULID 生成 / アプリ層の zod 検証（Phase 1-2）/
> BlobStore と作成・削除の順序（§3）/ 受け入れ形式の allowlist・シグネチャ検証・画像の配信（§4）/
> 上限（§5）（Phase 1-4）/ 一覧のページングと DELETE API への §3.2 の適用（Phase 1-6）。
> **§6（`shares` テーブル）は Phase 2 で実装済み。** 本章は全て実装済み。

## 1. 基本方針

**エントリは1種類のテーブルに収める。** 「1エントリ = テキスト1つ、または画像1つ」であり、
テキストと画像が同居するエントリは作らない（投入口の設計と対応する。[03](./03-ux.md) §1）。

**画像の実体は DB に入れない。** メタデータだけを MySQL に持ち、バイナリは SeaweedFS（S3 互換）に置く。

## 2. `clips` テーブル

| 列 | 型 | 説明 |
|---|---|---|
| `id` | `char(26)` | **ULID**。主キー |
| `kind` | `enum('text','image')` | エントリの種別 |
| `text` | `mediumtext` NULL | `kind='text'` のとき本文。`kind='image'` では NULL |
| `blobKey` | `varchar(255)` NULL | `kind='image'` のとき S3 のオブジェクトキー。`kind='text'` では NULL |
| `mimeType` | `varchar(255)` NULL | `kind='image'` のとき **サーバーがシグネチャから判定した** MIME（§4.1 の allowlist 内） |
| `byteSize` | `int unsigned` NULL | `kind='image'` のとき実体のバイト数 |
| `fileName` | `varchar(255)` NULL | 元のファイル名。**ペースト経由では取れないので NULL を許す** |
| `createdAt` | `datetime` | 作成時刻 |

### 並び順とページング

**一覧の総順序は `id` の降順単独とする。** ULID は辞書順が生成時刻順なので、これがそのまま
「新しい順」（[03](./03-ux.md) §2）になる。

- **`createdAt` をソートキーにしない。** `datetime` は複数行が同値になりうるため、単独では
  50件ずつのページ境界で順序が一意に定まらず、**同じ行が2ページに出たり、どのページにも出なかったりする**。
  `createdAt` は表示用に持つ。
- **`id` は主キーなので、並び替えのための追加索引は要らない。** ページングのカーソルも `id` 単独
  （`WHERE id < :cursor ORDER BY id DESC LIMIT 50`）。
- ULID は**同一ミリ秒内でも単調増加する生成器**（monotonic）を使う。連続して貼っても順序が一意に定まる。
- **`kind` と NULL 可能列の対応は、アプリ層で保証する**（`kind='image'` なら `blobKey`・`mimeType`・
  `byteSize` が揃う）。DB の CHECK 制約でも表現できるが、Drizzle のスキーマ定義とマイグレーションの
  素直さを優先し、**アプリ層の zod 検証を正**とする。

### なぜ ID を ULID にするか

**辞書順が生成時刻順**だから。一覧の並び順とページングを `id` 単独で成立させられる（§2 並び順）。
連番を避けるのは、ID から総件数や作成ペースが読めるのを防ぐ程度の意味であって、それ以上ではない。

> ⚠ **ULID は認可トークンではない。** 先頭 48 ビットは生成時刻そのもので、残りの乱数部も
> 暗号学的安全性が仕様上保証されない。さらに本 PRD は**同一ミリ秒内で単調増加する生成器**を
> 要求しているため、**観測できた ID の近傍は探索しうる**。

したがって次を守る:

- **ULID の推測しにくさを認可の代わりに使わない。** 保護は認証で行う（[04](./04-auth-and-privacy.md) §3）。
- **共有を ULID に乗せない。** 「ID を URL に載せて渡せば共有できる」設計にはしない。
  clip の ID とは**独立した共有トークン**を別に発行する（§6 / [04](./04-auth-and-privacy.md) §3.1）。
  共有 URL に clip の `id` が現れるのは**トークンで開いた後の中だけ**であり、`id` 単独では何も開かない。

## 3. BlobStore

画像の読み書きは `BlobStore` インターフェース越しに行い、**呼び出し側は保存先を知らない**。

```
put(key, body, contentType) -> void
get(key) -> stream
delete(key) -> void
```

- **実装は S3 互換クライアント1つ**（接続先は SeaweedFS）。将来ローカルファイル実装や別の
  オブジェクトストレージに差し替えられるが、**MVP では複数実装を用意しない**（使わない抽象を
  先に作らない）。
- オブジェクトキーは `clips/<id>` とする。`id` が ULID なので衝突しない。
- **削除時は行の `blobKey` をそのまま使わず、`id` から導出したキーと一致するか確かめる。**
  一覧は壊れた行も表示して削除を促すため（§3.2）、削除 API には不整合な値が来うる。DB は
  「`blobKey` が自分の `id` に対応する」ことも「他の行と重複しない」ことも保証しないので、
  **その値を信じると別のエントリの実体を消す**。一致しないときは DB 行だけ消し、ログに残す。
### 3.1 作成の順序と補償

画像の作成は **S3 と DB をまたぐ二重書き込み**になる。**順序は S3 put → DB insert とする。**

- `id`（ULID）は書き込み前に採番するので、`blobKey`（`clips/<id>`）は put の時点で確定している。
- **DB insert に失敗したら、同じリクエストの中で put 済みの実体を best-effort で削除する。**
- **補償削除にも失敗したらそのキーをログに残す**（後から掃除できる手掛かりを残す）。
  この場合に残るのは orphan な実体だけで、**一覧には現れず誰にも見えない**。害は容量のみ。
- 逆順（DB insert → S3 put）にすると、put 失敗時に**実体を持たない行が一覧に出る**。
  投入は即保存（[03](./03-ux.md) §1.1）なので、**失敗したものが成功したかのように並ぶ**ことになる。

### 3.2 削除の順序

- **削除はエントリ削除と同時**（[03](./03-ux.md) §4）。順序は **S3 の実体 → DB 行**とする。
  途中で失敗したときに残るものが違うためである:

  | 順序 | 途中失敗で残るもの | 気づけるか |
  |---|---|---|
  | **S3 → DB**（採用） | 実体を失った DB 行 | **気づける**（一覧に壊れた行として現れる） |
  | DB → S3 | 参照されない実体（orphan） | 気づけない（誰からも辿れない） |

  どちらも異常だが、**気づける異常の方を選ぶ**。

  そのため、**一覧は壊れた行を落とさずに「壊れています」と表示する**（[03](./03-ux.md) §2）。
  黙って除くと気づけなくなり、この選択が無意味になる。かといって一覧全体をエラーにすると、
  無事なエントリまで見えなくなって受け渡しに使えない。

  ⚠ **この異常は行の構造からは分からない。** S3 の削除が成功して DB 行だけが残った場合、
  行のメタデータは正しいままなので、一覧 API の検証では通ってしまう。
  **実体の取得が失敗したことを画面側で拾って表示する**（`<img>` の読み込み失敗を見る）。
  一覧のたびに全件の存在を問い合わせる（N+1）ことはしない。将来それでは足りなくなったら、
  「S3 削除済み・DB 削除未完了」を表せる状態列を持たせる。

### 3.3 作成と削除で残す異常が逆になる理由

作成では**見えない異常**（orphan な実体）を、削除では**見える異常**（実体を失った行）を選んでいる。
順序はどちらも「S3 → DB」だが、残るものが逆になる。一貫しているのは順序ではなく次の原則である:

> **画面が嘘をつかない方を選ぶ。**

- 作成に失敗したものが一覧に並ぶと、**保存できたと誤解する**（即保存なので、なおさら確認しない）。
- 削除に失敗したのに一覧から消えると、**消えたと誤解する**。実際にはデータが残っている。

## 4. 受け入れ形式の検証と画像の配信

private データと**同一オリジン**から画像を配信するため、**何を受け入れるか**が安全性を決める。

### 4.1 受け入れ形式（allowlist）

**保存してよいのは PNG / JPEG / GIF / WebP のみ。**

| MIME | 判定に使うシグネチャ（先頭バイト） |
|---|---|
| `image/png` | `89 50 4E 47 0D 0A 1A 0A` |
| `image/jpeg` | `FF D8 FF` |
| `image/gif` | `47 49 46 38` (`GIF8`) |
| `image/webp` | `52 49 46 46` … `57 45 42 50`（`RIFF`…`WEBP`） |

- **`image/svg+xml` は受け入れない。** SVG はスクリプトを含みうる**能動コンテンツ**であり、
  同一オリジンで inline 配信すると、開いた時点でアプリのオリジンで実行される。認証済み API を
  操作されたり、他の clip を読み出されたりする **stored XSS** になる。
  **貼るのが常に自分とは限らない**（他人からもらった画像を中継する用途がある）ため、形式で弾く。
- **クライアントが申告した MIME を信用しない。** サーバーが実体の先頭バイトから形式を判定し、
  allowlist 外なら 415 を返して保存しない。`clips.mimeType` に入れるのは**サーバーが判定した値**。
- 将来 SVG を扱いたくなった場合は、①ラスタライズして保存する か ②cookie を共有しない別オリジンから
  配信する のどちらかを設計してから足す。**allowlist をただ広げるのは禁じ手**とする。

### 4.2 配信

`GET /api/clips/:id/blob` で server が S3 から取得してストリームで返す。

- **署名付き URL へのリダイレクトはしない。** 認証をアプリの cookie セッションに一本化しており
  （[04](./04-auth-and-privacy.md)）、S3 の口を外に出すとその原則が崩れる。SeaweedFS もホストに
  公開していない（[01](./01-architecture.md) §3）。
- レスポンスヘッダ:
  - `Content-Type`: **保存時にサーバーが判定した `mimeType`**（クライアント申告ではない）
  - `Content-Length`: `byteSize`
  - **`X-Content-Type-Options: nosniff`** — ブラウザによる MIME 推測を止める。allowlist を通っても、
    推測で別の形式として解釈される余地を残さない
  - **`Cache-Control: private, no-cache`** と **`ETag`**（下記）
- ダウンロード用途では `Content-Disposition: attachment` を付けた別経路を用意する（[03](./03-ux.md) §3）。

#### 再転送をやめる（条件付き GET）

**`no-cache` を使う。`no-store` ではない。** 混同すると、どちらかの要件が黙って壊れる。

| | 意味 | 使う場所 |
|---|---|---|
| `no-store` | **保存すること自体を禁じる** | `/s/*`（[04](./04-auth-and-privacy.md) §3.1。**失効の一部**なので緩めない） |
| `no-cache` | 保存はしてよいが、**使う前に必ずサーバーへ検証させる** | `/api/clips/:id/blob` |

**`no-cache` でも削除の反映は変わらない。** 検証のリクエストは毎回サーバーまで届き、行が消えていれば
304 ではなく 404 が返る。消えるのは**転送されるバイト列だけ**である。
`no-store`（＝毎回全部を取り直す）にする理由は、ここには無い。

- **ETag は `id` と `byteSize` から導く。中身のハッシュは取らない。** 実体は id に対して**不変**である:
  投入は毎回新しい ULID を作り（§2）、更新の経路が無く、削除は行と実体の両方を消す。
  **同じ id が別のバイト列を指すことはない。**
- **`If-None-Match` が一致したら、S3 に触らずに 304 を返す。** ETag が DB の行だけで決まるので、
  **ストレージへの往復が丸ごと消える**。
- ⚠ **`public` にしない。** private データを共有キャッシュに載せてよい理由が無い。
- ⚠ **304 に `Content-Type` / `Content-Length` を付けない**（本文が無いため。RFC 9110 §15.4.5）。
  代わりに **`ETag` と `Cache-Control` は 200 と同じものを載せる**——欠けると次回の検証が成立しない。

> **なぜ要るか**: サムネイルを作らない（[05](./05-roadmap.md) §確定事項）ので、一覧に出る画像は
> **常に原寸**である。ヘッダが無い状態では**ブラウザが再利用の根拠を1つも持てず**、一覧を開くたびに
> 全件分を取り直していた（実測: 12 件で 13.4MB）。サーバー自体は速い（同 1.26MB を ttfb 4ms /
> total 6ms で返す）ので、**遅さの正体は距離 × バイト数**であり、減らすべきはバイト数だった。

## 5. 上限

- **1エントリあたりの画像は 20MB まで。** 超えたら 413 を返し、UI はその旨を表示する（[03](./03-ux.md) §1）。
- **テキストは `mediumtext` の上限（16,777,215 バイト・UTF-8 換算）まで。** 実用上ここに当たることは
  想定しないが、**超えた入力をそのまま insert すると DB エラーで 500 になる**ため、書き込み前に
  検証して 413 を返す。利用者の入力に起因する失敗を、サーバの不具合として返さない。
- **`fileName` は 255 文字（`varchar(255)`）を超えたら切り詰める。** ファイル名はダウンロード時の
  既定名でしかなく、**長いという理由で投入を拒む価値がない**（ペースト経由ではそもそも無い。§2）。
  ただし列に収まらないものを insert すると 500 になるので、**S3 に put する前に丸める**。
- **総容量の上限・古いものの自動削除は設けない**（[05](./05-roadmap.md) §確定事項）。
- **1つの共有セットに入れられるのは 50 件まで**（§6）。一覧のページサイズ（[03](./03-ux.md) §2）に揃える。
  無制限にする理由がなく、既にある数字を使う。
- **共有トークンの寿命は 10 分**。UI で選ばせない——想定する使い方は「発行 → 渡す → 読ませる」で
  **秒から分で終わる**ため、選択肢を出しても**毎回どうでもいい判断を強いる**だけになる。
  短すぎたと分かったら定数を変える（[03](./03-ux.md) §6）。

> **テーブルは `clips` と `shares` の2つ。** ログイン試行の記録用テーブルは持たない
> （レート制限は MVP 外。[04](./04-auth-and-privacy.md) §2 / [05](./05-roadmap.md) §未実装）。

## 6. `shares` テーブル（共有トークン）

LLM のセッションのように**ログインできない受け手**へ、**選んだエントリだけ**を渡すための仕組み。
UI は [03](./03-ux.md) §6、認証上の位置付けは [04](./04-auth-and-privacy.md) §3.1 に書く。

| 列 | 型 | 説明 |
|---|---|---|
| `id` | `char(26)` | **ULID**。主キー。`clips` と揃える |
| `tokenHash` | `char(64)` unique | 共有トークンの **SHA-256（hex）** |
| `clipIds` | `json` | 対象 clip の `id` の配列 |
| `expiresAt` | `datetime` | 失効時刻（発行の 10 分後。§5） |
| `createdAt` | `datetime` | 作成時刻 |

- **トークンそのものは保存しない。** 平文は発行時に一度返すだけで、DB に置くのは SHA-256 のみ。
  **DB が漏れても、そこから生きた共有 URL を組み立てられない**ようにする。
- **`permissions` 列は持たない。** 権限の種類はいま1つしかない（そのセットを読む）。
  **選ばれた clip の集合そのものが権限である。** 値が1種類しかない列は作らない。
- **`revokedAt` は持たず、失効は行の削除**とする。10 分で消える行に履歴を残す意味がなく、
  `expiresAt` の判定に条件が増えるだけになる。
- **`clipIds` に外部キーは張らない**（JSON 列なので張れない）。これは妥協ではなく、**望む挙動と
  そのまま噛み合う**: clip を消しても ID は残り、参照時に**現存する clip だけを引けば**、
  消えたものは自然にマニフェストから落ちて 404 になる。
  **共有中であることを理由に削除を止めない**（[03](./03-ux.md) §4 の「削除は破壊操作」を共有が上書きしない）。
- **`clipIds` の構造はアプリ層の zod で保証する**（§2 の `kind` と NULL 可能列と同じ分担）。
- **期限切れ行の掃除は、新しい共有を作るときに行う。** 同時に生きる行はせいぜい 1〜3 個で、
  cron を持ち込む規模ではない。
- **状態を Redis / Valkey に置かない。** TTL が組み込みである利点は本物だが、この機能のためだけに
  サービス・クライアント依存・2つ目の真実の在り処を増やすのは釣り合わない
  （[`_grilling/decisions.md`](./_grilling/decisions.md)）。
